What broke on Windows while generating a TypeScript SDK from OpenAPI

Generators are most useful when they remove repetition. Testing one on a less forgiving environment is useful for the opposite reason: it exposes the assumptions hidden inside the happy path.

Bruno Minhava08 Oct 2026~7 min read

I recently built an unofficial TypeScript SDK for the Documenso v2 API using the Voxgig SDK generator. The task itself was deliberately time-boxed, which made the developer experience matter as much as the final generated code. I was not trying to hand-write a perfect client. I was trying to see how quickly I could go from an OpenAPI definition to a working SDK that I could inspect, test and call against the real API.

I did the work on Windows. That turned out to be useful, because several small assumptions that are invisible on a Unix-like system became visible almost immediately.

Starting point: OpenAPI in, SDK out

The attraction of an SDK generator is obvious: an API definition already contains a lot of structure. If a tool can turn that into entities, methods, types, tests and documentation, the developer gets a large amount of consistent code without writing each endpoint by hand.

For Documenso, the generated SDK exposed the API as semantic entities. The basic shape looked like this:

const client = new Documenso2SDK({
  apikey: process.env.DOCUMENSO2_APIKEY,
})

const documents = await client.Document().list()

That is a much nicer surface than manually building paths, headers and query strings for every request. The interesting part of the exercise, though, was not the syntax. It was getting from the generator's first command to a repository I trusted.

The first Windows-specific failure: spawning npm

The scaffold attempted to run npm automatically, but on my Windows environment that step failed with spawn npm ENOENT. The same project could continue once I entered the generated SDK directory and ran npm install manually.

This is a classic cross-platform tooling problem. A command can be installed and available to a human in a shell while still being unavailable to a child process depending on how the process is spawned, what executable name is used, and how the environment is inherited.

From a user perspective the important thing is not the internal cause. The important thing is that the scaffold had already created enough of the project for a manual install to recover it. That is much better than a failure that leaves an unknown half-state.

If I were improving this path, I would do two things: make command resolution explicitly cross-platform, and make the error message say what the recovery command is. Something as simple as “automatic npm install failed; run npm install in .sdk” turns a confusing failure into a short detour.

Version floors should fail clearly

I was using Node 22. During installation I saw EBADENGINE warnings from dependencies that required Node 24 or newer.

Warnings like this are easy to ignore because the installation can appear to continue. But generator tooling has a long dependency chain, and using a runtime below the supported floor creates ambiguity: if something fails later, is the generator wrong, is the project wrong, or am I simply running an unsupported Node version?

For developer tooling I prefer an early, explicit runtime check. If Node 24 is the real supported floor, the CLI should ideally tell me before scaffolding anything. It makes support easier for maintainers and removes one whole class of doubt for users.

Generated imports that looked valid but did not resolve

The next failure was more interesting. Generation stopped because an Aontu source file could not be found:

source not found: api/api-info.aontu

The file existed. The generated model referenced it like this:

@"api/api-info.aontu"

Changing the import to an explicitly relative path fixed the problem:

@"./api/api-info.aontu"

I had to apply the same pattern to several generated model areas such as entities, features, targets, flows and tests.

I would be careful about calling this a core Aontu bug. I encountered it through the generated Voxgig model, and I did not isolate every layer independently. What I can say confidently is that in my environment the generated imports did not resolve until they were made explicitly relative.

The positive part was the resolver output. It showed where the tool had looked, which gave me enough evidence to stop searching for a missing file and start questioning path interpretation instead.

Partial scaffolds create second-order failures

Because the first scaffold had not completed cleanly, the TypeScript target was missing. I added it explicitly with:

npx voxgig-sdkgen target add ts

I also hit a zero-byte .sdk/.jostraca file where a directory was expected. Renaming that file allowed the expected directory structure to be created.

These were not the headline problems, but they were a useful reminder that setup failures often create follow-up failures. Once a bootstrap process aborts halfway through, every later error has to be read with the possibility that the project is not in a normal state.

A robust generator should either roll back incomplete bootstrap work, or record enough state to resume safely. “Idempotent setup” sounds boring until you need it.

Generated tests can still contain platform assumptions

After generation succeeded, the TypeScript project itself hit another Windows issue. The test/build script used a Unix command:

rm -rf dist dist-test

That is fine in many shells and fails in a standard Windows command environment. I worked around it by cleaning the directories manually and running the TypeScript compilation and tests directly.

The result was encouraging: 296 tests were discovered, 295 passed, none failed, and one was skipped.

The distinction matters. The SDK code was healthy; the wrapper script was not cross-platform. Without separating those two things, it would be easy to report “tests fail on Windows” when the actual problem is only the cleanup command that runs before them.

For reusable developer tooling, I would avoid shell-specific filesystem commands in package scripts. A small Node script or a cross-platform package makes the intent portable and removes one more environmental variable.

Local tests were not enough

I also made a real authenticated request using the generated client. Calling Document().list() returned an empty list, which was the expected result for the account I used. That gave me a different kind of confidence than unit tests: authentication, request construction, transport and response parsing all worked together against the live service.

Finally, I pushed the project to GitHub and let CI and the documentation workflow run there. That caught a prose-quality issue in generated documentation that I would not have seen from the SDK test suite alone. After adjusting the source description and regenerating, the workflows passed.

The useful pattern was layered verification: generator succeeds → project compiles → unit tests pass → one real API call works → CI and documentation checks pass. Each layer answers a different question.

What I would change in a generator after this experience

None of the issues above made the core idea of generation less useful. They mostly showed where a good generator can make itself feel more reliable:

  • Resolve package-manager commands in a platform-safe way.
  • Check the Node runtime version before scaffolding.
  • Generate explicit relative imports when local path semantics matter.
  • Make setup resumable or cleanly reversible after an aborted scaffold.
  • Avoid Unix-only shell commands in generated package scripts.
  • Keep detailed errors. They shorten debugging much more than generic “generation failed” messages do.

The main lesson for me was that generated code is only part of the product. The install path, error messages, scripts and CI templates are also generated developer experience. If any of those make assumptions about the user's machine, the user experiences the whole generator as unreliable even when the SDK output itself is good.

That is why I like testing tools like this on Windows. It is not about proving one operating system is harder than another. It is about finding assumptions while they are still cheap to fix.
