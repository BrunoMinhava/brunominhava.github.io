Aontu · developer experience

My first Aontu project: the model clicked, the imports didn't

I first met Aontu inside a real SDK generator task. The composition model made sense quickly; the first-run path around imports and editor setup was rougher.

Bruno Minhava08 Oct 2026~6 min read

I first used Aontu while building a TypeScript SDK from the Documenso v2 OpenAPI definition with the Voxgig SDK generator. I had never used the language before, so my first impression came from trying to make a real project work rather than following a tutorial.

At first, Aontu looked like another configuration format. That description stopped being useful quite quickly. Its main idea is unification: different parts of a model can contribute values and constraints to the same structure, and Aontu combines them when they are compatible. If they conflict, evaluation fails instead of silently letting one file overwrite another.

That idea grew on me. The developer experience around it was less convincing.

The part that made sense

In the SDK project, I needed to add my author and repository metadata without editing every generated file. The project overlay contained declarations like these:

main: kit: author: {
  name: "Bruno Minhava"
  url: "https://github.com/BrunoMinhava"
}

main: kit: repo: {
  path: "BrunoMinhava/documenso-sdk"
}

Both statements contribute to main.kit. Instead of treating them as two unrelated objects, Aontu lets them become part of the same model.

For a generator, this is a good fit. Project-specific decisions can live in a small overlay while the larger toolchain model stays separate. I did not have to keep editing generated output and hoping my changes survived the next generation run.

That was the first point where I understood why Aontu exists. For a small application with a few settings, I would probably reach for something simpler. In a generator, where many files need to describe parts of one model, the composition becomes useful.

The import problem was harder than it should have been

The part that cost me the most time was import resolution.

When I ran generation in my environment, the generated SDK model contained imports in this form:

@"api/api-info.aontu"

The file existed. The path looked correct relative to the model directory. Still, generation failed because the resolver did not find it.

Changing the import to an explicit relative path fixed it:

@"./api/api-info.aontu"

The same pattern appeared in other model areas, including entity, feature, target, flow and test imports.

For an experienced Aontu user, adding ./ might be an obvious thing to try. For me, using the language for the first time, it was not. I was trying to work out whether the SDK structure was wrong, whether a file had not been generated, whether I had misunderstood the language, or whether the resolver was using a different base directory.

That is exactly the kind of problem that makes onboarding feel harder than the underlying technology actually is.

I would make local generated imports explicitly relative by default. If both forms are intended to work, I would expect them to resolve consistently across supported environments.

One thing I would keep is the detailed resolver output. Seeing the locations it had searched helped me narrow the problem down. The failure blocked generation, but at least it gave me useful information instead of a generic “file not found”.

Important distinction: I experienced this through a generated Voxgig SDK model. I would not call it a core Aontu bug without isolating the resolver separately. What I can say confidently is that the generated imports did not resolve in my environment until I made them explicitly relative.

The tooling is more complete than I expected

After the SDK task, I spent more time looking at Aontu itself.

The project has more tooling than I expected from a language I had only encountered inside a generator. There is formatting, validation, model inspection, provenance, JSON Schema export and an LSP. The project also maintains TypeScript and Go implementations against a shared specification.

That matters because a language like this can become difficult to debug very quickly. If multiple files contribute to one model, being able to ask where a value came from is much more useful than searching through files manually.

The LSP is also the right direction. Diagnostics, hover information and completion can move errors much closer to the point where they are introduced.

However, the editor onboarding still feels early. The documentation explains how to connect aontu lsp to VS Code, but there is no published VS Code extension that a new user can simply install and start using.

I think that is a meaningful gap. When someone is already learning a new modelling language, asking them to wire up a language server adds another task before they receive the benefits of the tooling.

A small official extension that handles syntax highlighting, the LSP and import diagnostics would make a large difference to the first experience.

A detail I liked: exact decimal values

One part of the language I did not use in my SDK project, but found interesting while reviewing the project, is its handling of exact decimal values.

subtotal: 0d19.99
shipping: 0d4.01
total: $.subtotal + $.shipping

The 0d values are exact base-10 decimals rather than ordinary binary floating-point values.

What interested me more was how the documentation treats the JSON boundary. It does not pretend that exactness automatically survives a normal JSON.parse. If a value needs to remain exact, the documentation recommends representing it appropriately at the boundary and validating that representation.

That is a small example, but I like the attitude behind it: if the system cannot guarantee something, it should not quietly claim that it can.

Where I would use it

I would consider Aontu when configuration is starting to behave more like a model: SDK generators, code generators, large schema systems, agent definitions, or projects where several files need to contribute to one consistent result.

I would not introduce it automatically into a small project with a handful of settings. A new language has a learning cost, and that cost should buy something useful.

My first experience with Aontu was mixed. The composition model solved a real problem cleanly and made sense once I saw it working inside the SDK generator. The import issue made the first experience rougher than it needed to be, and the editor setup still creates extra work for someone arriving fresh.

I would use Aontu again for the kind of problem it was designed for. Before recommending it more broadly, I would want the path rules and editor experience to become boring.

For a configuration and modelling language, boring is a compliment.
